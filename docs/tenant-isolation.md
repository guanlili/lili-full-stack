# 组织/租户隔离决策清单

模板**有意不包含**组织/租户层：外包交付的典型形态是一个客户一套部署，整个系统就是这个客户的项目，预埋的租户字段每次交付都要拆除。本文件是客户项目在 `PROJECT_CONTEXT.md` 第 3 节"是否存在组织/租户隔离"回答**是**时的决策与实施清单，不是已实现功能。连续多个客户都需要隔离时，再评估把本清单下沉为模板级能力。

## 1. 先判断要不要

| 场景 | 结论 |
|------|------|
| 一个客户一套部署，所有用户共享数据 | 不需要。禁止"顺手"加组织字段 |
| 一个部署内多团队，A 部门的数据 B 部门不可见 | 需要，按本清单实施 |
| 一个部署服务多个客户（SaaS 形态） | 需要，且数据保留、备份、导出都要按租户单独约定 |
| 只是按角色区分能看到的功能 | 不需要。用现有 RBAC（`require_permission`）即可，权限和数据隔离是两回事 |

## 2. 动手前必须回答的设计决策

| 决策 | 选项与建议 |
|------|-----------|
| 抽象命名 | 用 **Organization（组织）**，不用 Project。project 与"交付项目/仓库"语义冲突 |
| 隔离方式 | 行级 `organization_id`（推荐，贴合现有 SQLModel + Alembic + RBAC）；PG schema 或独立数据库仅在强合规要求时评估，备份恢复和迁移成本显著上升 |
| 成员关系 | 单组织（`User.organization_id`）最简单；多组织需要 `user_organization` 关联表 + 当前组织上下文 + 前端组织切换器 |
| 角色作用域 | 优先复用全局 RBAC，成员资格决定数据范围；仅当客户明确要求各组织自定义角色时才做组织级角色 |
| 管理员语义 | 超级管理员跨组织；组织管理员仅限本组织。401/403 语义不变：401 未登录，403 已登录但权限不足 |
| 个人数据 | `Job` 现有的 `owner_user_id` 模式保留；是否允许 `organization_id` 为空（个人数据）要显式决策并写入 `PROJECT_CONTEXT.md` |
| 跨组织操作 | 搜索、导入导出、后台任务默认限本组织；跨组织能力作为高危权限单独编码 |

## 3. 后端实施清单

1. **模型与迁移**：新增 `Organization`（及 `user_organization` 或 `User.organization_id`）；所有业务表加 `organization_id` 外键 + 索引，可空与否按第 2 节决策。Alembic 迁移必须包含历史数据回填（默认组织，或按 `owner_user_id` 归属推断），`upgrade`/`downgrade` 都要验证。生成后人工检查。
2. **查询作用域**：在 `backend/app/api/deps.py` 增加组织上下文依赖（如 `get_current_organization`），所有业务查询统一注入过滤。**权限判断不能替代资源所属组织的过滤**——`require_permission` 只挡功能入口，数据范围由组织过滤保证（同 [module-development.md](module-development.md) 规则）。
3. **越权返回**：访问其他组织的资源推荐返回 404（不泄露存在性），与权限不足的 403 区分语义。
4. **权限登记**：组织维度的页面与高危操作在 `backend/app/core/permissions.py` 的 `PAGES` 登记权限编码；`seed_permissions` 随之适配。
5. **审计**：`AuditLog` 记录 `organization_id`，跨组织操作必须留痕。
6. **账号管理**：管理员创建/导入账号时指定组织归属；用户自助注册的默认归属（拒绝、待审批、默认组织）要显式决策。

## 4. 前端实施清单

1. 多组织时提供组织切换器；**切换组织后不得复用上一个组织的缓存**——组织维度进入 query key，规则同"退出或切换用户不复用缓存"。
2. 列表筛选、导航按组织权限渲染；前端可见性不能替代后端过滤。
3. API 契约变化后运行 `cd frontend && npm run generate-client`，禁止手写 URL 或改生成文件。

## 5. 测试与验收

- 组织 A 成员访问组织 B 的资源：404（或按决策 403）；超级管理员例外策略单独测。
- 未加入任何组织的账号、被移出组织后的既有会话。
- 跨组织的导入、导出、搜索、后台任务。
- 迁移 `upgrade`/`downgrade` 在 `app_test` 上各跑一遍。
- 上述全部写入独立 `app_test` API 测试，标准同 [module-development.md](module-development.md) 第 3 步。

## 6. 禁止事项

- 不在模板里预埋半吊子 `organization_id`：没有统一查询过滤的租户字段比没有更危险。
- 不用前端隐藏页面替代后端组织过滤。
- 不让审计辅助函数决定业务数据是否落库或归属哪个组织。
